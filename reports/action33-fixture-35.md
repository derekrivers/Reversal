# R35-C: selector entry and fixture-selection lifecycle

The enclosing `0084be20` selector can now execute from its original entry through its first static initialization, without supplying selected club IDs or skipping initialization. It reaches **pre-`0094bf49 -> KERNEL32.dll!HeapSize`** through IAT slot `009670dc`, with original outgoing arguments **(heap=0, flags=0, block=0)**, before reading its receiver, selecting fixtures or consuming RNG. Its CRT exit-list base/end and heap state remain loader-zero. The enclosing selector has not returned, and the R33-B interior `0084c266` producer has not been reached from entry.

The specimen is the 7,192,576-byte PE32 x86 image SHA-256 `0c78e7da6d0bcb4603fa179449bbe6d1b6b5e1c627a22c445d14d489bd9bff86`. Addresses are virtual; range metadata separately records PE file offsets. Baseline is `eabc39b443d18ca59c88c211c65b5ea5d089ed52` (PR #124). Names below remain research labels. R33-B's [owner report](action33-owner-33.md) and retained oracle are context; their interior windows remain a separate execution domain.

## Entry, caller and input lifetime

The selector saves incoming ECX in EBX at `0084be42`, stores that receiver at frame-base `+0x24`, and ultimately returns with plain `RET` at `0084c4fb`. The full local assembly uses no incoming stack argument or incoming EDX value. This supports an ECX receiver/no-stack-argument contract; it does not establish a source-level class or a return value. The static epilogue restores EDI, ESI, EBP, EBX and the SEH chain. It has not executed in this experiment.

The focused native references contain one direct caller: `005cdac9` within `005cccd0`. Immediately before the call, `005cdac3` loads ECX from DWORD global `00dd7ee4`. There is no pushed selector argument in that two-instruction window. The caller instruction pair is decoded from the pinned PE, without a native operand export. The full caller and earlier caller branches are unexecuted.

Existing native state exports show two static receiver producers: allocation of 8 bytes at `00829dfe` or `0082cb1a`, conditional `0084b940` construction, and stores to `00dd7ee4` at `00829e2e` or `0082cb48`. Teardown tests the global at `00830464`, calls `0084be10`, forwards the pointer to `00944c94` and clears the global at `0083047e`. Those allocation, constructor, loader and teardown lifecycles are static dependencies, not executed here. No initialized selector rows or original club IDs have been produced.

The selector reads a signed DWORD row count at receiver `+0`, and a DWORD row-array pointer at `+4`. Row stride is `0x44`: a signed DWORD member count followed by DWORD club IDs at `+4,+8,...`. This layout can hold 16 IDs per stride; the selector does not independently enforce that bound in its observed accesses. Its stack ID and availability arrays also have 16 apparent elements. A valid original producer and its bounds must precede an admitted selection path; these shapes alone are not validation of any real input.

## Original entry execution and first blocker

The harness uses zero-filled virtual-tail globals, varied synthetic stack bytes, synthetic scratch registers and a synthetic SEH head. Four cases enter `0084be20` directly with ECX zero. Four others start a **separate caller interior window** at `005cdac3`: the original load obtains zero from `00dd7ee4`, and the real call enters the selector. Neither case class claims execution from `005cccd0` entry, an initialized receiver, or a whole-game caller. The selector does not dereference its receiver before this stop.

The original instructions set bit 0 at byte `00dd7160`, then call the array constructor at `0084be6f -> 009463af` with `(00dd7287,0x625,2,00453c30,00453c10)`. The helper's normal path invokes the constructor twice. Each `00453c30` calls a nested original array helper with base `object+0x71`, stride `0x49`, count 20, constructor `00453c50` and destructor callback `005a53c0`. Each nested constructor invokes original `0054a110` on `element+0x14`.

Consequently the original instructions write WORD 40, WORD 1972 and DWORD 1 at each of **40** produced date-record addresses, in two ordered groups. Full nonstack comparison permits exactly those stores, the selector initialization flag and the pending SEH link. The remaining static object bytes stay zero. Both original nested and outer array helpers complete their normal paths; exceptional cleanup/destructor paths remain unexecuted. The small `00453c30`/`00453c50` bodies are pinned PE decoding, explicitly distinguished from ranges with native operand comparisons.

The selector next pushes callback `0084c500` and executes `0084be79 -> 0094627a -> 0094620d`. At `0094620e`, it pushes the unchanged DWORD exit-list base from `00de4638`, then the original call at `00946214` enters `0094bef1` with argument zero. This continues the earlier R31-B registration frontier through a separate pinned PE-only decoded helper. Heap mode DWORD `00de4404` remains zero, so it bypasses the helper's mode-2/mode-3 branches and pushes the incoming block pointer, flags zero and heap handle from `00de4400`, also zero. Execution stops **before** `0094bf49`, the indirect import call. A PE import-table walk independently resolves IAT `009670dc` to `KERNEL32.dll!HeapSize`; the actual outgoing stack words are `(0,0,0)`.

The globals `00de4400`, `00de4404`, `00de4634` and `00de4638` are in the PE zero-filled virtual tail. Original CRT startup, heap creation and exit-list allocation have not run. All helper/registration/selector frames remain pending. No import or allocator is stubbed and no HeapSize or callback-registration return is fabricated. No receiver read, date gate, club lookup, RNG, fixture construction or match preparation has executed.

Across eight cases there are **8,520 original instruction steps** and **320 date initializer calls**. Every ordered call, callback receiver, date write address/width, outgoing HeapSize argument and all nonstack bytes are checked against independently authored expectations. Stack snapshots, final registers and ordered memory/trace hashes are retained observations; the harness does not independently reconstruct every stack byte or claim complete CPU/flag equivalence. The selector does not return, so its entry-to-return ABI is not execution-validated. Static checks cover **590 native-operand-compared instructions** and **79 PE-only decoded instructions** across 14 ranges; unvisited branches remain static evidence.

## Static path from inputs to R33-B's club-ID window

All instructions in `0084be20..0084c4fb` are compared with the pinned native assembly. The following is a **static contract** for the downstream control flow; none is promoted to executed coverage by the entry prefix above.

| Phase | Original sites and behavior |
| --- | --- |
| Initial shuffle | `0084be93..0084bf46` repeats for the receiver's row count. It draws `i=R(n)`, then repeatedly draws `a=R(trunc(n/150))` and `b=R(trunc(n/150))` until `j=i-a+b` is in `[0,n)`. It draws one member index for each selected row and swaps those DWORD club IDs in the backing array. The two selected rows or member cells can alias. The calls with bound zero remain present; the existing bounded RNG's zero-bound branch returns zero without a table draw. |
| Row/date gate | `0084bf62..0084bf7f` requires signed `word[00ae2c90] % 7 == row_index % 7`. Then `0054cfb0` is called once, and again when its signed AL is greater than 4; that branch rejects when the second signed AL is below 7. The PE-only decoded helper selects one of two embedded cumulative-word tables according to date DWORD `+4`, scans against date WORD `+0`, and returns AL. Its calendar meaning and exact table contents are not substituted here. |
| Candidate copying and date queries | Each row ID is copied into stack `F+0xb0+4*k` before eligibility work. `0084bfe6 -> 0054c8e0` receives output storage `F+0xa0` and delta 2; `0084c018 -> 0054c5b0` receives storage `F+0xa8` and delta 3, both with ECX `00ae2c90`. Here F is ESP after the selector's saved-register prologue. Their actual returned eight-byte values are copied, including overlapping DWORD loads used to marshal query arguments. These date bodies and their lazy initialization are unresolved transitive dependencies in this unit. |
| Existing-fixture query | At `0084c05c -> 005acbe0`, ECX comes from `00ae2a58`. The nine outgoing DWORDs are the two copied date pairs (assembled from DWORDs beginning at F offsets `0x98,0x9a,0x90,0x92`), club ID, `0,-1,-2,-1`, in callee argument order. Nonzero AX marks availability byte `-1`. The helper and manager lifecycle remain unresolved. |
| Staff availability | If AX is zero, the original computes `00ae23b4 + club_id*0x245`; null DWORD club `+0x53` also marks `-1`. Otherwise it scans **50 DWORD roster pointers** beginning at club `+0xd7`. Null staff and null staff `+0x61` are skipped. Nonnull candidates call `0062c400` using receiver `00b63d28`; AL 2 is skipped. Remaining candidates call `007757d0(staff,00ae2c90,club,0,0)` using receiver `00b74318`. A zero result increments the byte availability count. These callees may have transitive state/RNG effects; this unit does not declare them pure. |
| Sort and shuffle | `0084c159..0084c1c8` compares availability as **signed bytes** and swaps the paired IDs to sort descending, using strict improvement (equal bytes do not swap at that comparison). Byte `F+0x12` counts positive candidates. When its signed value q is greater than 2, `0084c1da..0084c221` makes q squared iterations, each drawing two `R(q)` values and swapping the corresponding count/ID pairs among the first q entries. |
| Pair gate and ownership | From `0084c249`, first availability must be positive and second availability must be **greater than signed -1**, so zero is allowed for the second club. `EDI=F+0xb4` initially. R33-B's `0084c266` loads home ID from `[EDI-4]` and away ID from `[EDI]`, then calculates their pointers using stride `0x245`. Club IDs and their order therefore depend on the original earlier shuffle, date queries, availability calls, sorting and optional second shuffle. Supplying those IDs skips all these dependencies. |

The later call `0084c339 -> 0090d2f0`, allocation, match constructor and `0084c3e8 -> 006b7f20` remain downstream context. In particular, the existing R33-B owner binding does not establish selector-entry continuity or completed prepare-match behavior. The fixture is the selector's stack storage at `F+0x40`; it has not been produced by this entry experiment. R35-B's `00ae2d0c` auxiliary-table work is a separate dependency and evidence domain.

The private [verifier](../scripts/verify_action33_fixture_35.py) requires byte-identical original-instruction regeneration in normal and optimized Python. Thirteen negative probes reject changed specimen/manifests, an executed wrong date value, a missing callback, wrong outgoing heap flags, a resealed wrong store width, raw/hex/base64 private fragments and excessive decompression. The bounded privacy scan covers compressed evidence, expanded JSON and authored task files. The oracle retains synthetic stack/state observations, authored scalar facts, addresses and hashes; original code, bulk listings and native data remain private. The [Node checker](../scripts/check-action33-fixture-35.mjs) checks ordered calls/writes, provenance, public artifact integrity and two independent semantic mutations. This integration registers it in the shared runner; the registry, frontier and queue remain unchanged.

The checker passes both directly and through repository `npm run check` under Node **24.19.0**. Normal and optimized Python also run the verifier's negative gates.

The first remaining dependency is the pending original Windows import at `0094bf49`; completing it requires an admitted OS/CRT heap lifecycle and the exit-list state that the caller expects. After that, the selector still needs the original receiver constructor/rows, date state and callees, eligibility managers, club/staff database and shared RNG. There is no TypeScript selection implementation, connected fixture selection, full match preparation, live fixture or completed game claim.
