# R37-A: bounded Windows reference capture helper

The [capture helper](../scripts/reference_capture_37.py) can identify a running x86 WOW64 process, map a preferred executable VA to its runtime module, and take a bounded context/memory sample from one selected thread. Its `watch` mode samples for **pre-call VA `007023e3`**, the pending `R(2)` variant draw in [R36-A](action33-selector-36.md). A sampled EIP match is recorded explicitly; an exhausted watch reports that the boundary was not observed. Sampling cannot guarantee interception of a brief instruction boundary.

The implementation was first exercised against a separate, harmless 32-bit Windows PowerShell child. The first coordinator-requested game inventory attempt failed at `OpenProcess(QUERY_INFORMATION | VM_READ)` with Windows error 5 (access denied). The user subsequently ran `inventory` in administrator PowerShell. Its private result authenticates the pinned disk executable against a live image at module base `0x00400000` and maps preferred `0x007023e3` to runtime `0x007023e3`; it lists four threads. That inventory had zero probes. A later administrator-run snapshot suspended and resumed one game thread for one context and stack read while idle, away from the target boundary. The snapshot includes x87 and extended-register context, but neither run established match-time RNG or floating-point state or reached the target boundary. The coordinator's separate UI save-load observations are outside this tool's evidence.

## Identity and scope

The game profile requires disk executable SHA-256 `0c78e7da6d0bcb4603fa179449bbe6d1b6b5e1c627a22c445d14d489bd9bff86`; changing the expected hash is available only through an explicitly labelled `synthetic-test` profile. That profile rejects the pinned game hash to prevent mislabelling game captures. Both profiles require a PE32 x86 executable, its process image path, a uniquely identified loaded module, matching module size, and matching live DOS/PE signatures, machine, timestamp and image-size fields. These checks authenticate the disk input and selected live identity fields; they do not prove that loaded code was never modified.

All addresses are integers in JSON. Each accepted capture records UTC time and the capture script's SHA-256. The boundary record distinguishes preferred VA, RVA, runtime VA and file offset. For the pinned disk PE, preferred base is `00400000`, boundary RVA is `003023e3`, and file offset is `003023e3`. The runtime VA is **observed module base + RVA**. The failed non-elevated attempt obtained no runtime base; the later elevated inventory did. This equality of RVA and file offset at this particular site is a PE-layout fact, not a general conversion rule.

The host implementation requires 64-bit Python, Windows x64, `IsWow64Process2`, and the WOW64 context APIs. Native x64/ARM and exited targets, self-targeting, mismatched image/hash, unrelated thread IDs and already suspended threads are rejected. Inventory uses process query/read access, module snapshots and a live header read, with no thread suspension. Snapshot/watch additionally request thread context, query and suspend/resume rights. Access denied is a failed capability, even when a limited-query process handle worked elsewhere. The helper does not request privilege elevation or retry access failures.

## Capture contract

| Mode | Behavior |
| --- | --- |
| `inventory` | Hash/PE/process/module checks and target thread IDs; no context sampling |
| `snapshot` | Suspend one explicitly selected thread, read its x86 GPRs/EFLAGS, legacy x87 and extended context, 128 stack bytes and optional explicit regions, then resume |
| `watch` | Repeat bounded suspend/context/resume probes of one selected thread; retain context/memory only at exact sampled boundary EIP; stop at first hit or configured limit |

No debugger attachment, breakpoint installation, target memory writes, context writes, game launch or UI interaction is performed. Suspending affects scheduling. The helper balances its own suspension increment in `finally`, including context-read failures and rejection of a pre-suspended thread. Concurrent suspend-count changes are rejected. Forced termination of the capture process can bypass Python cleanup. Other target threads remain running, so a context plus memory reads is **not an atomic whole-process snapshot**.

Hard limits are 128 distinct module records, 64 target threads, 1,000 probes, 30 seconds for the sampling loop, 8 explicit regions, 4,096 bytes per region and 16,384 requested sample bytes including the 128-byte stack. A separate live PE-header read is bounded to 4,096 bytes. Initialization/hash/API time is outside the sampling-loop time limit. Combined Toolhelp module flags yielded an exact duplicate main-image record on the safe test host; only identical records are deduplicated. Distinct records remain visible. Inventory over the module/thread limits is rejected.

Every memory read records requested/received byte counts, success/completeness, Windows error, SHA-256 and the actual returned bytes. Missing bytes are not zero-filled or treated as captured. `memory_complete` can be false even on a boundary hit; consumers must inspect it and each read. It is null when no memory sample exists. Empty inventory/miss sample lists contain no captured stack or object state. Inventory records no suspension or context read. Pointers are native addresses; no object-graph completeness, portable fixture, call ordering, event ordering, normal gameplay reachability, deterministic replay or outcome equivalence follows from them.

## Reproduction

Run from this checkout with 64-bit Python, using a coordinator-controlled working copy and its actual running PID. The helper never starts the game. Use a fresh output name for every invocation:

```powershell
python scripts/reference_capture_37.py inventory --pid GAME_PID --exe WORKING_COPY_EXE --output results/reference37-inventory-01.json
python scripts/reference_capture_37.py snapshot --pid GAME_PID --exe WORKING_COPY_EXE --thread THREAD_ID --output results/reference37-snapshot-01.json
python scripts/reference_capture_37.py watch --pid GAME_PID --exe WORKING_COPY_EXE --thread THREAD_ID --samples 100 --seconds 5 --interval-ms 10 --output results/reference37-watch-01.json
```

Replace uppercase placeholders with the actual values. Select the intended thread from the private inventory and validate its role; the tool does not infer a simulation thread or assume that the match path is active. The snapshot can validate available context access before attempting a short watch. Watch is opportunistic: a miss cannot distinguish an unreached boundary from an instruction executed between samples. Reliable interception, return tracing and ordered writes would require a separately reviewed debugger/probe capability.

`--region 0xRUNTIME_ADDRESS:SIZE` requests an explicit bounded read at a **runtime** address. The boundary argument uses a preferred VA instead; the game profile fixes it to `0x7023e3`. For a verified loaded base `B`, optional four-byte RNG scalar addresses are `B + (00de1f60 - 00400000)` (cursor), `B + (00de1f5c - 00400000)` (offset), `B + (00de2798 - 00400000)` (limit), and `B + (00ad6c30 - 00400000)` (CRT seed), from the existing RNG harness. These are read locations, not validated runtime values. The full random table and pointed-to objects are not automatically captured. Derive additional regions from an evidenced register/object layout and stay inside the capture budget.

Raw output is allowed only beneath this checkout's ignored `results/`, with exclusive file creation; its parent directory must already exist. The standalone command reuses the guarded Windows output writer in `reference_capture_broker_37.py`, which locks each output-directory ancestor against replacement and rejects reparse points. Capture refusals write an explicit `capture_accepted: false` record. Serialization or buffered-write failures delete the incomplete file through its open handle; existing output is never replaced. The earlier game attempt used the pre-hardening implementation and left an empty reserved file, not a capture. Do not interpret that empty file as evidence. Standard output contains a compact status or error, no raw memory or personal paths. Module paths are omitted from the JSON inventory, but memory, registers and module names remain private material. This location is local preservation only; this unit establishes no durable backup. The coordinator must inventory/backup any useful future capture privately before relying on its preservation.

The non-elevated game attempt performed disk identity validation and then failed at the first process-handle request with `WinError=5`. No module/thread snapshot, live header read, context API or suspension occurred in that attempt. The elevated inventory succeeded and wrote a private 9,020-byte result, SHA-256 `432b698844166cdae89f9bf4bd62639e262eeb961de2979c4b2a5279d5e40f51`. Its live module image size is 10,383,360 bytes and its preferred-to-runtime mapping is recorded; no thread was suspended or sampled. This historical result used the pre-fix inventory reporter: its `memory_complete: true` and generic suspension descriptions are metadata errors. Its `mode: inventory`, zero probes and empty samples show the actual scope. The raw result and hash are preserved; future inventory output reports no memory sample and no suspension explicitly. An administrator PowerShell snapshot then sampled thread 28368 once, producing a private 11,302-byte result, SHA-256 `770a3491dcecd744e72b76aa6c50b63eb1f4ffc4b368451b29d5095f9cd4a1c4`. It read a complete 128-byte stack and found EIP `0x756511ac` in `win32u.dll`, away from the reviewed game boundary. This verifies context and memory-read access while that thread was idle. A useful boundary capture and match-time thread identification remain unverified.

## Verification and evidence limits

The [checker](../scripts/check_reference_capture_37.py) launches only its own [synthetic target](../scripts/reference_capture_37_synthetic.ps1), with no visible window. The target allocates bytes `00` through `3f`, reports only its own address/PID to the private test, waits for input, then frees the allocation and exits. The checker verifies actual Windows module/thread APIs, a complete 128-byte stack read, the exact 64-byte allocation and digest, nonzero EIP/ESP and x87 control, extended context length, explicit failed address-zero read, a three-probe exact-boundary miss, balanced suspension cleanup and normal target exit. A deliberately altered **local context copy** tests hit-path retention and first-hit stopping; it neither modifies the target nor establishes a real boundary hit.

Twenty-two negative checks cover wrong hash, game hash/profile misuse, unsupported x64 PE, unrelated/missing thread, an explicit thread for both sampled modes, opened-handle owner mismatch, count/time/region/budget limits, out-of-image boundary, self/exit/pre-suspended targets, an injected access-denied API result, failed context cleanup, output collision, failed-output labelling, incomplete-output deletion after a circular JSON result and public-path rejection. The opened thread's owner is checked again before suspension to reject a recycled thread ID. All integrity checks use explicit exceptions and remain active under optimized Python.

```powershell
python scripts/check_reference_capture_37.py --output results/reference37-commit-normal.json
python -O scripts/check_reference_capture_37.py --output results/reference37-commit-optimized.json
npm run check
git diff --check
```

Python 3.13.7 and Node 24.19.0 were used. The normal/optimized synthetic receipts are byte-identical; both checks pass, including optimized child CLI execution. The full repository check passes under Node 24.19.0. Public changes contain source, synthetic support and this report; private memory/context captures and personal paths are excluded. The Windows-only task checker is standalone; no shared runner/queue/registry or canonical native state is edited.

Microsoft documents that [valid WOW64 contexts require thread suspension](https://learn.microsoft.com/en-us/windows/win32/api/wow64apiset/nf-wow64apiset-wow64getthreadcontext), that [suspend/resume changes a suspend count and affects scheduling](https://learn.microsoft.com/en-us/windows/win32/api/wow64apiset/nf-wow64apiset-wow64suspendthread), and that [memory reads require `PROCESS_VM_READ` and accessible requested ranges](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-readprocessmemory). These API contracts informed the tool; the safe local tests above establish the behavior actually exercised on this host.
