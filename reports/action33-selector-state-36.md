## Static row construction and load format

The complete constructor, destructor and row loader have native operand comparisons. None of the following downstream row behavior executes through the OS stops above.

1. The zero-argument constructor requests a temporary DWORD-ID array of `4 * DWORD[00ae235c]` bytes using 32-bit arithmetic at `0084ba73..0084ba81`. Its null-result path invokes diagnostics and exit-related callees. It does not produce a successful receiver on the observed prefix.
2. For a positive signed database count, `0084bb0d..0084bb85` scans club records with stride `0x245`. Each club's DWORD pointers at `+0x57` and `+0x60`, when nonnull, supply an index from their first DWORD into the pointer table at `00adadfc`. A nonzero table element excludes that club. Otherwise `00775790(club)` is called with receiver from `00b74318`; only its zero result accepts the club. The accepted DWORD ID comes from club `+0`, not from substituting the loop index. These database/manager lifecycles and the transitive helper are unresolved.
3. With nonnegative, nonoverflowing accepted count n, `0084bb8f..0084bbb3` stores row count `ceil(n/16)` at receiver `+0`. The original signed divide/remainder construction is retained in assembly; no blanket arithmetic contract is asserted for overflowed or invalid state.
4. `0084bbb6..0084bc48` orders accepted IDs descending by the **signed WORD** at their club record `+0x80`, swapping only when the left word is smaller. `0084bc4a..0084bcba` then makes `trunc(n/2)` swap iterations. Each chooses a center `R(n)`, then repeats the two calls `R(trunc(n/150))` until center-minus-first-plus-second lies in range. Swaps and every retry share the original RNG order; no fresh generator or no-op shuffle is substituted.
5. `0084bcc0..0084bcd7` requests `row_count*0x44` bytes and stores the returned pointer at receiver `+4`. There is no intervening null-result guard before downstream row accesses. The row loop writes a DWORD count zero at each row base and copies DWORD IDs to row `+4+4*count`, incrementing each count. The remaining unused row bytes are not blanket-zeroed by this code.
6. The original packing rule requires care. Let r be n modulo 16 for admitted nonnegative counts. Each row normally takes 16 IDs, but when r is nonzero and `row_index < 16-r`, it stops after 15. This is the actual branch at `0084bd9c..0084bdcc`; it is not replaced with a general balancing algorithm. Small arbitrary n can exhaust the input list before this rule fills the allocated rows: `0084bd0e` compares the consumed count with n and takes a diagnostic path on equality, then continues if the diagnostic callees return. No small-count caller domain, diagnostic return policy or safe packing invariant has been established by execution here.
7. The temporary ID array is passed to `009452ca` at `0084bdee` before the static receiver-return tail. The backing rows remain referenced by receiver `+4`, for the later selector or destructor. Actual ownership and failure handling require allocator and caller lifecycle evidence.

For a **nonzero constructor argument**, `0084ba5f` calls `0084c510` and then returns the receiver even though the helper's EAX success value is not checked. The helper passes the supplied argument and an embedded resource-name pointer to `009326e0`, then on success uses `00932c30` to read one four-byte item directly into receiver `+0`. It allocates `count*0x44` bytes, publishes that allocation at receiver `+4`, and requests `count` items of size `0x44` into it. The success path calls `00932b00` and returns EAX 1 with RET 4; failures take diagnostics and return zero. Those file/resource operations, original serialized count/rows, allocator and failure cleanup remain unexecuted. No row format is inferred from a synthetic file, and no substitute file handle is supplied.

This establishes how R35-C's static `+0/+4`, `0x44`-stride row shape can be produced, with explicit unresolved callees and domain constraints.
