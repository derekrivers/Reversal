# Four exact receiver-cleanup shapes across 143 function entries

The investigation-08 atlas contains 9,241 inferred internal functions. This census identifies **143 non-`Unwind@` entries** whose complete contiguous native bodies match four operand-aware templates: 52 at 201 bytes, 43 at 191 bytes, 28 at 135 bytes and 20 at 180 bytes. All 143 were decoded from the pinned 3.9.68 PE (`0c78e7da6d0bcb4603fa179449bbe6d1b6b5e1c627a22c445d14d489bd9bff86`). The four samples were also compared instruction by instruction with a read-only Ghidra 12.1.4/JDK 21 checkpoint-16 export. The sample-export manifest SHA-256 is `e5df99ec062265fe66277a9d1dc09887472fea081132a51471e54b6e49614393`.

These functions are **mechanical receiver cleanup**, not 143 recovered game algorithms or proven original C++ destructors. The repeated `ECX` receiver, exception-frame setup, literal written to receiver offset 0, conditional pointer handling and final helper calls support that local description. Object types, ownership and transitive helper effects remain open. The two immediate literals masked during matching are recorded for every row; their apparent metadata/table roles are not treated as original declarations.

| Template | Entries | Complete local instruction shape |
| --- | ---: | --- |
| A201 | 52 | 62 instructions. Register an FS:[0] frame; write a unique large literal to receiver+0; conditionally pass pointers at +`0xa7` and +`0xa3` to `009452ca`; if +`0xad` is nonnull, visit each pointer in its array using signed word count +`0x3c`, release nonnull elements, then pass the array pointer to `009452ca`. If receiver+8 is nonnull, call `0049f450` on it then `00944c94` with it. Finish with `00518690`, restore the frame and return. No direct zeroing of those pointer fields is observed. |
| B191 | 43 | 60 instructions. Frame and receiver+0 literal; call `00687970(0)`; conditionally pass +`0xba` to `009452ca`, then zero +`0xba`. If signed dword +`0x30` is nonnegative, visit slots **0 through count inclusive** in the array at +`0xc`; for each nonnull slot, call its first indirect table target with pushed argument 1. If +`0xc` is nonnull, pass it to `009452ca` and zero the field. Conditionally process receiver+8 through `0049f450` and `00944c94`; finish with `00682300`, restore frame and return. |
| C135 | 28 | 38 instructions. Same frame, receiver+0 literal, `00687970(0)`, conditional +`0xba` release and zero, conditional receiver+8 pair, and `00682300` tail cleanup as B191, without B191's +`0xc` counted-array loop. |
| D180 | 20 | 57 instructions. Same counted-slot traversal as B191, but it passes receiver+`0xc` to `009452ca` **unconditionally** after the loop and does not zero +`0xc`. The rest follows B191's frame, +`0xba`, receiver+8 and final-helper shape. A zero/invalid +`0xc` is therefore a callee boundary, not locally guarded. |

For B191 and D180, the slot loop tests the signed +`0x30` field at entry and reloads it after each callback. A callback can change the next loop bound. The indirect call through each nonnull slot's first table pointer has no statically resolved target. These shapes do not prove element lifetime or that `009452ca` accepts every pointer state; the `00682300` local body was mapped in investigation 16, but its own callees remain transitive boundaries. Exceptional paths and runtime invocation conditions are also unresolved.
